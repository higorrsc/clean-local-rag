# AGENTS.md

## Project Development Guidelines

This repository contains a Python-based Local RAG (Retrieval-Augmented Generation) application designed according to **SOLID**, **Domain-Driven Design (DDD)**, **Clean Architecture**, and **Spec-Driven Design (SDD)** principles.

The AI agent must treat this document as the primary development guideline for the repository and must preserve the architectural boundaries defined here.

The goal is to produce software that is:

- maintainable;
- testable;
- modular;
- framework-independent at the domain level;
- explicitly contracted via OpenAPI;
- entirely local and secure (no external LLM providers);
- easy to evolve from a CLI to a REST API.

---

# 1. General Principles

The following principles are mandatory:

- **Single Responsibility Principle**
- **Open/Closed Principle**
- **Liskov Substitution Principle**
- **Interface Segregation Principle**
- **Dependency Inversion Principle**

Avoid:

- LangChain or LlamaIndex (we manage prompts and orchestration manually for total control);
- Framework-dependent domain logic;
- Infrastructure dependencies inside domain entities.

---

# 2. Clean Architecture

The application must be organized around RAG business rules rather than frameworks (like Typer or FastAPI).

The dependency direction is:

```text
Presentation (CLI / Typer)
     ↓
Application (Use Cases)
     ↓
Domain (Interfaces, Entities)
     ↑
Infrastructure (Ollama via httpx, pgvector via psycopg)
```

Inner layers must never depend on outer layers.

---

# 3. Suggested Architecture

The repository follows a clean, modular structure:

```text
rag_project/
├── openapi.yaml          # The single source of truth for contracts
├── pyproject.toml        # Managed by uv
├── docker-compose.yml    # Ollama + PgVector infrastructure
├── .env.example          # Environment variables template
└── src/
    ├── config.py         # Centralized pydantic-settings
    ├── domain/
    │   ├── interfaces.py # Protocols (EmbeddingGateway, VectorRepository)
    │   ├── models.py     # Generated by datamodel-code-generator from openapi.yaml
    │   └── entities.py   # DocumentChunk, etc.
    ├── application/
    │   └── use_cases.py  # IngestDocumentsUseCase, AskQuestionUseCase
    ├── infra/
    │   ├── ollama_adapter.py  # httpx calls to local Ollama
    │   └── pgvector_adapter.py # psycopg raw SQL with pgvector
    └── cli.py            # Typer CLI application (Composition Root)
```

---

# 4. Domain Layer

The domain layer contains the application's business rules and interfaces.

It must not know how persistence (`psycopg`), HTTP (`httpx`), or CLI (`Typer`) work. It relies on Python's `typing.Protocol` to define contracts that infrastructure will implement.

## 4.1 Entities & Models

Entities encapsulate invariants (e.g., `DocumentChunk`).
Request/Response models are strictly generated from the OpenAPI specification to enforce Spec-Driven Design.

---

# 5. Application Layer (Use Cases)

The Application Layer orchestrates the RAG pipeline.

A Use Case should:

1. Receive input (validated by generated OpenSpec models).
2. Invoke the Embedding Gateway to vectorize text.
3. Coordinate the Vector Repository (save or search).
4. Invoke the LLM Gateway with an augmented prompt.
5. Return the application result.

Use Cases must be independently testable using Fake Repositories/Gateways, without needing the real Ollama or Postgres containers running.

---

# 6. Spec-Driven Design (SDD) & Pydantic

The project uses **OpenAPI (`openapi.yaml`) as the definitive source of truth**.

- You must NOT manually create Request/Response DTOs for the boundaries.
- Models must be generated using `datamodel-code-generator` based on `openapi.yaml`.
- The CLI (`cli.py`) and future API controllers must consume these generated Pydantic models.

Workflow:

```text
openapi.yaml -> datamodel-codegen -> src/domain/models.py -> Application Layer
```

---

# 7. Dependency Injection

Dependencies must be injected rather than instantiated inside business logic. The `cli.py` acts as the Composition Root.

Prefer:

```python
# cli.py
repo = PgVectorAdapter(conn_str=settings.pg_dsn)
embedder = OllamaAdapter(base_url=settings.ollama_base_url)
use_case = IngestDocumentsUseCase(embedder, repo)
use_case.execute(req)
```

---

# 8. Infrastructure: Database (pgvector)

This project uses raw SQL with `psycopg` and `pgvector`. **Do not introduce ORMs like SQLAlchemy or Django.**

- Vector operations (e.g., Cosine Similarity `<=>`) must be handled natively in Postgres via `pgvector`.
- The `PgVectorAdapter` must implement the `VectorRepository` Protocol.
- Connection strings should come from environment variables.

---

# 9. Infrastructure: External Services (Ollama)

This project uses local models exclusively (`qwen3:4b-instruct`, `nomic-embed-text`).

- Do not use OpenAI, Anthropic, or external APIs.
- Do not use LangChain. Use `httpx` to make direct REST calls to `http://localhost:11434/api/`.
- The `OllamaAdapter` must implement `EmbeddingGateway` and `LLMGateway` Protocols.

---

# 10. Presentation: Typer CLI

The current presentation layer is a CLI built with `Typer`.

- It must not contain RAG business logic.
- It is responsible for parsing terminal arguments, instantiating infrastructure adapters, injecting them into Use Cases, and printing the results.

---

# 11. AI Agent Development Workflow

When an AI coding agent is used, it must follow:

1. Read `AGENTS.md`.
2. Check `openapi.yaml` for contract changes.
3. Generate Pydantic models if the spec changed.
4. Implement/update `src/domain/interfaces.py`.
5. Implement/update `src/application/use_cases.py`.
6. Implement/update infrastructure (`infra/`).
7. Update `cli.py`.
8. Write/Run tests.
9. Format (`ruff format`) and Lint (`ruff check`).

The agent must not bypass architectural boundaries (e.g., calling `httpx` directly inside a Use Case).

---

# 12. Testing Strategy

Testing is mandatory.

- **Domain/Application Tests:** Must use Fakes/Mocks for `VectorRepository` and `LLMGateway`. Should execute in milliseconds.
- **Integration Tests:** May spin up Postgres/Ollama containers to test the actual `PgVectorAdapter` and `OllamaAdapter`.
- **E2E Tests:** Execute the Typer CLI commands directly.

---

# 13. Dependency Management (uv)

The project uses `uv` for dependency management.

- Do not use `pip`, `poetry`, or `pipenv`.
- To add a package: `uv add <package>`
- To run a script: `uv run python src/cli.py`

---

# 14. Environment Configuration

Application configuration must be centralized using `pydantic-settings`.

- Do not use `os.getenv()` scattered throughout the codebase.
- Define a central `Settings` class in `src/config.py`.
- Never commit the `.env` file if it contains real secrets. Provide a `.env.example` documenting the required variables (e.g., `PG_DSN`, `OLLAMA_BASE_URL`).

---

# 15. Git Workflow & Conventional Commits

All commits must follow the **Conventional Commits** standard. This ensures a readable project history, automated versioning, and clear communication between developers and AI agents.

## 15.1 Commit Message Format

```text
<type>[optional scope]: <description>
```

*Example:* `feat(cli): add ingest command for markdown files`

## 15.2 Allowed Types

- **feat**: A new feature (e.g., adding a new CLI command, Use Case, or OpenAPI route).
- **fix**: A bug fix (e.g., correcting the vector cosine similarity calculation).
- **docs**: Documentation changes (e.g., updating `README.md`, `openapi.yaml`, or `AGENTS.md`).
- **refactor**: A code change that neither fixes a bug nor adds a feature (e.g., extracting logic into a Domain Service).
- **test**: Adding missing tests or correcting existing tests.
- **chore**: Changes to the build process, auxiliary tools, or dependency updates via `uv`.
- **perf**: A code change that improves performance (e.g., optimizing database queries).

## 15.3 Gitmoji Integration

To improve visual scanning of the history, combine Conventional Commits with Gitmoji:

- ✨ `feat:` add vector search use case
- 🐛 `fix:` correct text chunking logic
- ♻️ `refactor:` decouple Ollama client from application layer
- ✅ `test:` add unit tests for PGVectorAdapter
- 📝 `docs:` update openapi.yaml schemas
- 🔧 `chore:` add pydantic-settings via uv

## 15.4 Pre-Commit Checklist

Before staging and committing, the agent or developer must ensure the codebase respects the project's quality standards:

1. Run the formatter: `uv run ruff format .`
2. Run the linter: `uv run ruff check .`
3. Run the tests: `uv run pytest`

Never use `git commit --no-verify` or bypass failing tests to force a commit unless explicitly justified by the architectural context.

---

# 16. Definition of Done

A feature is considered complete only when:

1. The contract is defined in `openapi.yaml`.
2. RAG logic (chunking, retrieval, prompt assembly) is isolated in Use Cases.
3. Infrastructure (SQL queries, HTTP requests) is isolated in Adapters.
4. Typer CLI commands accurately reflect the OpenSpec inputs.
5. Tests pass.
6. `uv run ruff check` and `uv run ruff format` pass.
7. Commits follow the Conventional Commits and Gitmoji standards.
8. No external LLM providers or heavy abstraction frameworks (LangChain) were introduced.
